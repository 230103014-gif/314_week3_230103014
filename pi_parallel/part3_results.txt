QUESTION 1

At 8 threads, the runtime was 136.473 ms, while at 16 threads
it decreased only to 122.412 ms. This represents approximately
a 1.11x improvement rather than 2x.

Doubling the number of software threads does not double the
physical CPU resources. Once the available physical cores are
saturated, additional threads must share execution resources.
This introduces scheduling overhead, context switching, cache
contention, and resource competition.

This is also visible in the parallel efficiency, which decreased
from 40.47% at 8 threads to 22.56% at 16 threads.


QUESTION 2

The synchronized version took 2238.820 ms, while the
single-threaded version took only 282.184 ms.

Slowdown = 2238.820 / 282.184 ≈ 7.93x

The synchronized version was slower because all four threads
repeatedly competed for the same lock protecting totalHits.
Only one thread could increment the shared counter at a time,
so this part of the program became effectively serialized.
The repeated lock acquisition, waiting, scheduling, and cache
synchronization overhead outweighed the benefit of using
multiple threads.
